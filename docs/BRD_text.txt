2. Executive Summary
Road Accident Hotspot Mapping is a data-driven, web-based geospatial platform that helps traffic police, road safety analysts and transport authorities identify, analyze and prioritize accident-prone locations (hotspots or black spots). Using geospatial analysis, machine learning and AI techniques, the system imports and cleans road accident records, locates them on an interactive map, detects statistically significant accident clusters, scores and classifies each hotspot by risk, analyzes contributing factors, recommends road safety interventions, and tracks each hotspot through to resolution on a centralized dashboard.
The platform is designed as a human-in-the-loop decision-support tool: all hotspot rankings and recommendations are advisory and must be validated by qualified road safety professionals (for example through field surveys) before any engineering, enforcement or policy action is taken.
Core value chain: Collect → Validate → Analyze → Map → Prioritize → Recommend → Track
3. Business Context and Problem Statement
3.1 Background
Road accidents cause a significant number of deaths, injuries and economic losses every year. Accident data is recorded by multiple agencies (police stations, highway authorities, hospitals and municipal bodies) in different formats such as FIR registers, spreadsheets and reports. Much of it lacks accurate coordinates, which makes it difficult to see where accidents concentrate and why. As a result, limited road safety budgets are often allocated on the basis of experience or complaints rather than evidence.
3.2 Problem Statement
To locate dangerous road stretches and plan corrective measures, road safety teams typically have to:
Manually collect and consolidate accident records from multiple sources and formats
Clean data and locate accidents on maps by hand, often from textual addresses or landmarks
Identify locations with repeated or severe accidents using spreadsheets
Investigate contributing factors such as time of day, weather, road type and vehicle type
Prioritize locations for intervention within limited budgets
Track whether implemented interventions actually reduced accidents
This manual process is time-consuming, error-prone and heavily dependent on individual experience. It delays the identification of dangerous locations, increases the risk of repeated accidents and makes it hard to measure the impact of safety measures.
3.3 Proposed Solution
Road Accident Hotspot Mapping automates the repetitive parts of accident data analysis. It ingests and validates accident records, geocodes and maps them, detects and ranks hotspots, classifies risk levels, identifies contributing factors, recommends safety interventions, supports assignment and tracking, and retains history so that the effect of past interventions can be measured and reused in future planning.

Integration with real-time traffic, weather and navigation data sources

Mobile application for field survey and public reporting of unsafe locations
Email and SMS notification channels
Learning from expert feedback to improve recommendations

8.2 Detailed Requirements and Acceptance Criteria
FR-01: User Authentication and Access Control
The system shall allow users to register and log in, enforce role-based access control, and allow administrators to manage users, roles and permissions.
Acceptance criteria: (a) A registered user can log in with valid credentials and is denied with invalid ones. (b) Each role can access only the features permitted in the role–permission summary, and the Public Viewer sees only aggregated data. (c) An administrator can create, edit and deactivate users and change roles.
FR-02: Accident Data Import and Management
The system shall allow authorized users to add accident records manually or import them in bulk from CSV / Excel files. Each record shall receive a unique accident ID and capture date, time, latitude and longitude (or location description), road name and type, severity (fatal, grievous injury, minor injury, non-injury), number of fatalities and injuries, vehicle types involved, weather and light conditions, and probable cause where available.
Acceptance criteria: (a) A unique ID is generated for every accident record. (b) All mandatory fields are validated before saving. (c) Supported file types, a maximum file size and a standard import template are defined, and unsupported files are rejected with a clear message. (d) An import summary shows the number of records accepted and rejected.
FR-03: Data Validation, Cleaning and Geocoding
The system shall validate imported records, detect duplicates, missing or out-of-range values and invalid coordinates, standardize formats (such as dates and severity categories), and geocode records that contain only an address or landmark.
Acceptance criteria: (a) Seeded duplicates and invalid coordinates in a test file are detected and reported. (b) Records with only an address are geocoded and flagged with a geocoding confidence. (c) A data quality report (accepted, corrected, rejected) is stored against each import. (d) Rejected records can be corrected and re-submitted.
FR-04: Hotspot Detection and Spatial Analysis
The system shall analyze validated accident data using spatial analysis and machine learning techniques (for example kernel density estimation and DBSCAN clustering) to identify accident hotspots along road segments and at junctions. Authorized users shall be able to configure analysis parameters such as search radius, minimum number of accidents, time period and severity weighting.
Acceptance criteria: (a) Seeded accident clusters in a test dataset are detected as hotspots. (b) Each hotspot shows the number of accidents, fatalities and injuries and the analysis period. (c) The parameters used are stored with the results so the analysis is reproducible. (d) If the data is insufficient, the system states that no reliable hotspot can be determined rather than guessing.
FR-05: Risk Scoring and Classification
The system shall compute a severity-weighted risk score for each hotspot, classify it by risk level according to the table below, and allow authorized users to override the AI-suggested risk level.
Acceptance criteria: (a) Every hotspot has a risk score and a risk level. (b) Scoring weights and thresholds are configurable by an administrator and displayed to users. (c) Overrides are recorded in the audit trail with user, time and reason.
Risk Level
Definition
Critical
Very high concentration of fatal or grievous-injury accidents; requires immediate attention
High
High accident frequency or severity; priority for intervention
Medium
Moderate accident frequency; requires monitoring and planned improvement
Low
Few or low-severity accidents; routine monitoring
FR-06: Interactive Map Visualization
The system shall display accidents and hotspots on an interactive map with heatmap, cluster and marker layers, color-coded by risk level, with zoom, pan and pop-up details. Users shall be able to filter the map by date range, time of day, severity, road type, weather, vehicle type and area.
Acceptance criteria: (a) Map markers and hotspots match the underlying data. (b) Filters update the map correctly. (c) Selecting a hotspot shows a summary of its accidents, risk level and status. (d) The map loads within the agreed performance target.
FR-07: Contributing Factor Analysis and Safety Recommendations
The system shall analyze contributing factors for each hotspot (time of day, day of week, weather, light conditions, road type, vehicle type and recorded causes) and generate recommended safety interventions such as signage, speed calming, street lighting, junction redesign or enforcement. Experts must review recommendations before taking action.
Acceptance criteria: (a) A factor summary is generated for every hotspot with sufficient data. (b) Each recommendation is linked to the factor(s) it addresses and shows supporting evidence. (c) The interface clearly labels recommendations as AI-generated and requiring expert review.
FR-08: Hotspot Tracking and Action Management
The system shall allow users to view hotspots, assign them to responsible officials or engineers, update status, add comments, record interventions and maintain resolution history. Users shall be able to search and filter hotspots by status, risk level, road or area, assignee and date, and compare accident counts before and after a recorded intervention.
Acceptance criteria: (a) Status follows the defined lifecycle. (b) Comments are timestamped and attributed. (c) Search and filters return correct results. (d) A before / after comparison is available for any hotspot with a recorded intervention date.
FR-09: AI Insights Assistant
The system shall provide a conversational interface where users can ask questions such as which are the top hotspots in an area, at what time most fatal accidents occur at a location, what factors contribute to accidents at a hotspot, which interventions are recommended, and whether accidents have reduced since an intervention.
Acceptance criteria: (a) Answers are grounded in the stored accident data and analysis results. (b) The assistant cites the hotspot or data used. (c) Out-of-scope questions receive a polite refusal or redirection.
FR-10: Notification System
The system shall notify relevant users when a Critical hotspot is detected, a hotspot is assigned, a risk level changes, or an intervention is marked as implemented. For this release, notifications are delivered in-app; email and SMS are future enhancements.
Acceptance criteria: (a) Notifications are generated for each listed event. (b) Only relevant users receive them. (c) Users can view and mark notifications as read.
FR-11: Dashboard and Analytics
The dashboard shall display total accidents, fatalities and injuries; number of hotspots by risk level; accidents by severity, road type and area; time-of-day and day-of-week distributions; and accident trends over time. Users shall be able to export reports.
Acceptance criteria: (a) Figures match the underlying accident data. (b) Data can be filtered by date range and area. (c) Reports can be exported in PDF or CSV format. (d) The dashboard loads within the agreed performance target.
FR-12: Data Privacy and Sensitive Data Masking
The system shall detect and mask or remove personal identifiers (such as victim or driver names, contact numbers, vehicle registration numbers and licence numbers) in imported data before they are stored or sent to any external LLM or third-party service.
Acceptance criteria: (a) Seeded personal identifiers are masked in stored data and in LLM requests. (b) Masking is applied before analysis begins. (c) The public view displays only aggregated, anonymized data.
FR-13: Audit Trail
The system shall record data imports, record edits, analysis runs and hotspot activity, including who made each change and when.
Acceptance criteria: (a) Import, assignment, status change, risk override, analysis run and comment events are logged. (b) Audit records cannot be edited by regular users.

11. Data Requirements
Accident data: ID, date, time, latitude, longitude, location description, road name and type, severity, fatalities, injuries, vehicle types, weather, light condition, probable cause (personal identifiers masked)
Hotspot data: hotspot ID, location / road segment, geometry, accident count, risk score, risk level, status, assignee, timestamps
Analysis output: parameters used, clusters, contributing factors, recommendations, supporting evidence, confidence indicators
Geospatial reference data: base map tiles, road network, administrative boundaries
User data: profile, role, authentication credentials (hashed)
Activity data: import logs, data quality reports, comments, notifications, audit records, assistant conversations
Retention: retention period and deletion rules for accident data and analysis results to be defined with the faculty guide
12. Assumptions, Constraints and Dependencies
12.1 Assumptions
Accident data provided is reasonably complete and contains coordinates or addresses that can be geocoded
Users have a stable internet connection
Road safety experts are available to review analysis results and validate hotspots
12.2 Constraints
Map, geocoding and cloud-based LLM services require internet connectivity
Hotspot accuracy depends on the quality, completeness and reporting coverage of accident data (under-reporting may bias results)
Analysis output must always be validated by qualified professionals
Personal data must be masked before external processing
Physical road interventions require approval by the competent road authority
The project must be completed within the academic calendar and available team resources
12.3 Dependencies
Availability, licensing and rate limits of map and geocoding providers (e.g. OpenStreetMap-based services)
Availability, pricing and rate limits of the chosen LLM provider
Cloud hosting platform for deployment
Public, sample or synthetic accident datasets for development and testing

18. Conclusion
Road Accident Hotspot Mapping transforms scattered accident records into an intelligent, evidence-based and auditable road safety workflow. By combining geospatial analytics, machine learning and AI-assisted insights with action tracking, the platform helps road safety teams locate dangerous stretches faster, understand why accidents occur and prioritize interventions more effectively, while keeping qualified professionals firmly in control of every decision.
Core Business Value: Collect → Validate → Analyze → Map → Prioritize → Recommend → Track
